# Local character animation

Use the supplied character image as the identity reference. Generate2-3 complete demonstrations of the same motion when source time permits; select one whole candidate, never mix demonstrations or include source-only resets. Preserve a one-shot's intended ending. Before input preparation, read [specification confirmation and clean delivery](references/specification-guide.md) and run `scripts/comfyui_forge_animation_spec.py` for the numbers. Use the user's language. First use: propose final128x128,1s with8fps as an initial output default, dynamic4-16fps; ask adopt Yes/No. On No collect only final size and playback seconds, not fps. Ask only source resolution with numbered choices:1 performance512x512,2 balanced768x768(default),3 quality1024x1024. Source fps is fixed24; choose requested seconds from2-3 times final duration, capped15s including actual aligned duration. Source tiers are fixed canvases, not multiples of final dimensions. Above16 final fps requires explaining the need and receiving explicit user approval, hard maximum24; do not infer approval from delegated4-16fps assessment. Before EVERY generation, including later tasks in the same chat, display the two-part current specification summary required by the guide. Same-chat tasks may reuse accepted settings without asking again, but never omit the summary or treat saved settings as authorization for unrelated work.

## Evaluate the action reference before generation

Apply this assessment to any requested animation, not just named actions or built-in templates. Infer the intended pose, facing, expression, motion phases, framing and gameplay constraints from the user's text and character image. A sketch or pose reference is optional; do not require one. Descriptive motion names are free text, never routing keys. Choose reasonable unspecified details and ask only about ambiguities that materially affect the result.

- If the supplied pose, view and framing can plausibly lead into the intended motion, use it directly. Otherwise, consider an action-specific first frame before submitting video: a large pose/view change, tight clearance or likely clipping can make repeated video attempts ineffective.
- Preserve identity, proportions, costume and colors while designing the action pose and safe framing. Check the full silhouette against any height/space constraint at a consistent character scale; shrinking, stretching or rotating the entire still is not proof of a correct pose.
- Check which image tools are actually available and the user's service preferences. An already authorized external image tool may prepare a separate input asset; if external use is not authorized or conflicts with local-only preferences, ask before using it. Never seek API keys, silently switch services or introduce a provider fallback. With no suitable tool, accept an action still supplied by the user or use their explicitly configured local image workflow; explain the limitation rather than promising generation.
- Show a newly prepared action still for user approval before submitting video. Treat it as an input asset to this skill, retain the original identity reference, and use the approved pose to generate appropriate motion; do not reduce an action that needs substantial movement to an unrequested stationary hold.
- For distinct motion phases, assess whether separate clips and transition references are needed. A first frame does not guarantee the whole motion. Describe the actual motion and its spatial constraints. No named action templates are selected or inferred. Disclose unsupported workflow controls instead of inventing flags.

This optional input-preparation step does not add still-image generation or a cloud route to ComfyUI-Sprite-Forge. Its video adapter continues to use local ComfyUI only.

## Plan motion space and gameplay behavior

Before preparing input or submitting video, read [motion planning and acceptance](references/motion-planning.md). Apply it to any action: frame the complete motion envelope of the body and all attached parts across the whole animation, use centred placement only as a starting default, preserve the planned placement and shared scale through delivery, assign translation to the game or animation, plan state transitions and loop behavior, and isolate local motion only when requested. Generation canvas and final game cells are separate; never silently crop, squash or change one action's scale to fit. Inspect the prepared input before submission and the actual animation before acceptance. Before a framing retake, announce the observed clipping and planned correction; proceed without approval unless the repeated-deviation checkpoint applies. After two consecutive reviewed generations with the same deviation, pause before the third and offer the user a choice to relax that condition or keep trying. If they insist, announce a different attempt method; prompt changes and seed changes each qualify. Follow the motion-planning reference for counting attempts, preserving criteria and job/seed integrity.

## Pipeline

1. Use `scripts/comfyui_forge_video2dsprite.py doctor` to check ffmpeg/ffprobe. Check generation with the sibling `../comfyui-forge-generate2dmedia/scripts/comfyui_forge_media.py --check`; no GPU submission.
2. Choose the behavioral contract from [generic motion and background handling](references/prompt-rules.md). Prepare with `scripts/comfyui_forge_prepare_i2v_input.py prepare --master IMAGE --motion-type TYPE --description DESCRIPTION --canvas WIDTH,HEIGHT --duration SECONDS --output-dir NEW`. TYPE is cycle, oneshot-return or oneshot-hold. Use confirmed dimensions/seconds and plan motion margins explicitly. Preparation preserves genuine alpha or attempts automatic extraction of any consistent opaque flat background by estimating all four edges. Check the extracted master on light/dark backgrounds and keyChoice.preflight; select a contrasting generation backdrop without changing subject colours. Only stop for user repair if extraction fails or its result cannot reliably preserve the subject. Never edit the user's source.
3. Prepare the prompt for 2-3 complete action candidates (prefer3, completeness first), using the source resolution and duration calculated for this task; separate one-shot demonstrations instead of a combo. Generate through `../comfyui-forge-generate2dmedia/scripts/comfyui_forge_route_media.py video --route comfyui --reference INPUT --prompt-file PROMPT --duration SOURCE_SECONDS --out-dir NEW`. When input and prompt are prepared together, pass --preparation registration_job.json so their hashes are verified before submission. Use --last-frame only for a suitable action and a bound tail input. Never retry a pending/unknown submission in a new folder.
4. `scripts/comfyui_forge_video2dsprite.py process` keys and decodes; inspect matte-report and actual frames. Use `scripts/comfyui_forge_register_clip.py apply` (automatic canvas padding retries once only for intact source overflow, without changing scale) or documented tracking for a consistent scale and planned anchor. Follow the translation ownership decision: remove unwanted root travel when the game owns it, preserve intended pose motion and bob, and do not universally lock feet. Registration padding can accommodate intact motion, but cannot restore clipped source pixels.
5. Select ONE complete candidate before time warping. A continuous cycle uses `scripts/comfyui_forge_gait_loop.py select --frames-dir FRAMES --fps SOURCE_FPS --kind cycle --policy cycle --output-dir NEW`; inspect phase/velocity continuity, not just matching endpoint poses. Either one-shot type normally uses `comfyui_forge_retime.py --kind TYPE --range START:END --auto-oneshot --duration-ms FINAL_MS --output-fps FINAL_FPS --output-dir NEW`. The range is one reviewed full demonstration, excluding source-only resets. Do not infer events or phase percentages from its name. Define reviewed source-frame keys/holds only when required by the motion. Retain the initial pose and the intended terminal pose, including a complete recovery when the contract requires it.
6. `scripts/comfyui_forge_finish_frames.py hd --frames REGISTERED --target-height 104 --canvas 128x128 --canvas-anchor 64,116 --output-dir NEW` illustrates the finishing syntax; choose target height and canvas anchor from the reviewed motion envelope and planned placement rather than copying these example values. Preserve the shared scale and directional clearance; inspect and resolve any canvas-fit warning before acceptance. Do not stretch the source to square or resize each frame to its own alpha bounds.
7. Standard finalization: run `scripts/comfyui_forge_finalize_animation.py prepare --finished FINISHED --selection SELECTION --spec SPEC --source MP4 --work-dir NEW`, inspect preview.gif and the light/dark review-contact.png, then run its `approve --work-dir WORK --out-dir OUTPUT --review-note TEXT`. This verifies source/finish hashes and available source-video provenance, materializes exact final playback slots, including intentional holds from the retimed selection, recalculates final seam/drift and records visual acceptance. It uses `scripts/comfyui_forge_deliver_animation.py` with exactly the finished selected RGBA PNGs and the confirmed specification. It exports selected PNGs, a transparent fixed-cell sheet, GIF preview and original source MP4, and makes a ZIP containing only those four kinds. Put its optional receipt at a work-directory `--report` path. Render GIF/sheet/source in the conversation, link the ZIP and retained work directory, and caption cell size/count/layout/baseline timing. Inspect the actual animation and light/dark matte edges. Standard delivery is PNG frames, sheet, GIF preview and source MP4; unrelated transports and engine runtimes are not supplied.

Each command's --help gives full flags. References cover registration, matte, finishing and standard delivery. No automatic retakes merely for an install check.

## Timing and receipts

Choose the lowest final fps that clearly preserves the motion and rhythm: start at8fps, reduce redundant sampling to6 or4, or increase to10/12/14/16 when necessary transitions are lost. Distinguish source defects from sampling loss; more output frames cannot fix missing or incorrect source motion. Above16fps needs a concrete visual justification and explicit user approval before producing the higher-rate sprite sheet; final fps must stay within4-24. Assess before generation and validate the actual final-size playback afterward. Before selection/retiming, announce the assessed fps, total frame count, preserved playback duration and reason;4-16fps needs notice only, above16 requires approval first. Preserve duration and intentional holds; fps is not total frame count except for a1-second animation. Follow the specification guide for delegated rate adjustments and confirmation.

Standard sheets use one row for4 or6 frames (and other counts below8), and two rows for8 or more: columns=ceil(frameCount/2). Layout follows the delivered total frame count, not fps. Read left-to-right then top-to-bottom, keep equal fixed cells, and identify any trailing empty cell as unused. Change this layout only when explicitly requested.

1second at8fps means8 output frames at125ms each. GIF is limited to10ms timing ticks and binary alpha: use alternating120/130ms for a1s preview and retain125ms in the work timing receipt. Use a whole motion period from the longer source, not simply eight evenly spread frames including holds.

pending: resume the same generation folder. unknown: inspect local queue/history. done: checksum-verify and reuse the clip. Report identity changes, deformation, camera drift, seam or matte warnings; a tool success is not art approval.

## Local installation

This unofficial fork uses ONLY local ComfyUI for generation. No cloud providers, API keys, CLI generation or automatic code-art fallback. Built-in still-image generation is not configured; use supplied images or an approved action still prepared separately under the assessment above.

Keep the three animation-core skills together: generate2dmedia, generate2dsprite and video2dsprite. This fork contains only the three animation-core skills. Use only this project's scripts or their installed copies, never another project's skill programs. Keep the declared Python/FFmpeg dependencies and configured local ComfyUI connection. Find the permanent repository and configured JSON in `<skills-root>/.comfyui-sprite-forge.install.json` (`project`, `comfyuiConfig`). Use that repository's `.venv/Scripts/python.exe` on Windows or `.venv/bin/python` elsewhere, or another Python with the documented dependencies. Do not copy the author's paths or alter original Sprite Forge settings.

The adapter finds configuration from explicit COMFYUI_FORGE_CONFIG, then the installed manifest, then repository-local local-comfyui/config.local.json. No global environment changes are required. Read the configured API JSON before adapting a workflow; the user's ComfyUI must already run it.

### Three motion contracts, arbitrary motions

- `cycle`: continuous motion repeats through a matching moving phase. Seam evaluation includes velocity; no artificial stationary boundary or synthetic reverse playback.
- `oneshot-return`: one complete action recovers to its initial pose. Matching first/last poses do not make it continuous. Play once.
- `oneshot-hold`: one complete action ends in its intended terminal pose. Play once and retain that pose; never force recovery.

Choose a contract from the user's intent; clarify only when materially ambiguous. Timing, key poses, local holds, translation ownership, support constraints and spatial margins follow this particular request, not a motion-name list. All three source types can contain2-3 complete same-motion demonstrations for comparison. Select one; never combine demonstrations or include source-only resets. Candidate completeness and artistic acceptance require visual review.

Pass the selected/retimed selection.json to comfyui_forge_finalize_animation.py. It inherits durations, exact ticks and events and quantizes them to the confirmed frame rate. Plain cycles use phase sampling; authored rhythm is retained for any type. Intentional holds may repeat PNG poses. Inspect timing errors and dropped transitions in review.json; necessary poses exceeding the frame budget cause an error rather than silent loss. The final review must verify the behavioral contract, subject integrity, final-size readability and all matte edges. A type declaration records intent, not proof of generated behavior.

### Review revisions

See `references/sprite-set.md` for per-take `select --timing-file` revisions. Keep generation plans immutable, preserve prior reviews/deliveries, and reuse the same source clip. Arbitrary legal event labels pass through unchanged; no whitelist or `custom:` prefix is required. Inspect recorded QC failures together with final visuals before accepting. Review GIF/contact sheets and finished frames are hash-checked at delivery. For changed or legacy local stage caches, use `rebuild --from-stage` on the same take as documented in `references/sprite-set.md`; it preserves the source video and never submits generation. A key phase that cannot fit the confirmed playback grid stops with an explanation rather than moving silently.

When the executable workflow provides a seed socket, new generation submissions receive a random integer seed recorded in the job and submitted graph. Workflows without a seed socket skip seed assignment and submit normally. Resume and completed-artifact reuse retain that frozen seed; never resubmit to change the seed of an existing job.
